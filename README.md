# Тестовое задание МАВИКО

## Работа с документацией и ИИ

ИИ использовался как помощник при проектировании решения, проверке технических гипотез, подготовке тестовых сценариев и code review.

Моделям передавались:

- текст тестового задания;
- требования к каждому этапу;
- предполагаемая архитектура решения;
- названия и назначение методов Ozon Seller API;
- структура фактических API-ответов;
- результаты read-only диагностических запросов;
- структура и отдельные примеры строк `catalog_raw.csv`;
- результаты тестов и найденные ошибки.

Запросы формулировались так, чтобы модель отдельно разделяла:

1. подтверждённые факты о работе API;
2. инженерные решения проекта;
3. предположения, которые ещё необходимо проверить.

Также модели явно указывалось не выдумывать поля API-ответов и не использовать неподтверждённые методы или response fields без проверки по документации или реальному read-only запросу.

Для Task 3 сначала исследовались реальные данные из `catalog_raw.csv`, после чего уже формулировались правила нормализации и парсинга. Неоднозначные значения не должны были угадываться.

Критичные решения дополнительно проверялись другими ИИ-моделями как независимый second opinion. При расхождениях окончательным источником истины оставались документация, реальные API-ответы и тесты.

## Как проверялись ответы ИИ и актуальность API

Ответ модели сам по себе не считался подтверждением.

Для проверки использовались:

- официальная документация Ozon Seller API;
- changelog API;
- реальные read-only запросы к предоставленному тестовому кабинету;
- фактические JSON-ответы API;
- unit и regression tests.

Например, первоначально `/v3/product/info/list` рассматривался как возможный источник всех необходимых данных о товаре.

После проверки реальных ответов было установлено, что для production-выгрузки цена и остатки корректнее получать через отдельные методы:

- `/v5/product/info/prices` — цена;
- `/v4/product/info/stocks` — остатки.

Также отдельно проверялась пагинация. Реальный API мог вернуть короткую страницу с непустым `last_id`, поэтому условие `len(items) < limit` не использовалось как признак конца списка. Пагинация продолжается по `last_id`/`cursor` до пустого continuation token.

## Task 3: крайние случаи и неоднозначные данные

Перед написанием очистки был исследован предоставленный `catalog_raw.csv`.

В данных встретились:

- цены в разных форматах: с пробелами, точкой, запятой, суффиксами `руб`, `р`, `rub`;
- значение `от 450 руб`, которое интерпретировано как нижняя граница цены `450.00`;
- строка без цены;
- строка без `offer_id`;
- количество в форматах `шт`, `комплект`, `набор`, `пара`;
- `комплект` без явного количества;
- размеры вида `600мм/400мм`, которые нельзя ошибочно принимать за количество;
- несколько строк одного товара с совместимыми данными;
- потенциально конфликтующие строки, которые нельзя безопасно объединить без однозначного правила.

Главный принцип очистки: неоднозначные значения не угадываются.

Записи объединяются только тогда, когда идентификатор совпадает, цены не противоречат друг другу и данные об остатках совместимы. Конфликтующие строки не объединяются автоматически.
